# Deploy on AWS with Terraform

[`deploy/aws/terraform`](../deploy/aws/terraform) creates the whole AWS test environment from [Deploy on EC2](deploy-ec2.md) in one command, deploys the app, loads the sales sample into Redshift and fills in the app's connection settings. `terraform destroy` removes all of it.

## What it creates

All in us-east-1, in the default VPC, tagged `Project = ontodata`:

| Resource | Name | Notes |
|---|---|---|
| Security groups | `ontodata-ec2`, `ontodata-services` | Port 4000 open to your current IP only. Redshift, RDS and Neptune accept the app server only. |
| Redshift Serverless | namespace and workgroup `ontodata` | 8 RPU base capacity, private. Database `dev`, admin `ontodata_admin`, read-only app user `ontodata`. |
| RDS PostgreSQL 16 | `ontodata-pgvector` | `db.t4g.micro`, 20 GB, private, no backups. Database `vectors`. Created when `vector_store = "pgvector"` (the default). |
| S3 vector bucket | `ontodata-vectors-<account>` | The app creates the index on first sync. Created when `vector_store = "s3vectors"`. |
| Neptune | `ontodata-neptune` | `db.t4g.medium`, IAM auth on. **Off by default**; turn on with `enable_neptune = true`. |
| IAM role | `ontodata-ec2` | Systems Manager access, S3 Vectors, Neptune, and reading the deploy bundle. |
| S3 bucket | `ontodata-deploy-<account>` | Holds the zipped project for the instance. |
| EC2 instance | `ontodata-app` | Ubuntu 24.04, `t3.large`, Docker. Metadata hop limit 2. |
| SSM association | `ontodata-deploy` | Runs [`deploy.sh.tftpl`](../deploy/aws/terraform/deploy.sh.tftpl) on the instance. See [What the deploy does](#what-the-deploy-does). |

Passwords are generated by Terraform and kept in its state file, `deploy/aws/terraform/terraform.tfstate`, which is git-ignored. You never need to type them: the deploy puts them into the app's settings.

## One-time setup

### 1. Create the deployer user

In the IAM console, signed in as an admin:

1. **Policies → Create policy → JSON**, paste [`deploy/aws/deployer-policy.json`](../deploy/aws/deployer-policy.json), and name it `ontodata-deployer`.
2. **Users → Create user** `ontodata-deployer`, with no console access. Attach the `ontodata-deployer` policy.
3. Open the user, go to **Security credentials → Create access key**, choose **Command Line Interface (CLI)**, and copy the two values.

### 2. Save the key on your machine

Create the folder `C:\Users\<you>\.aws` and two files in it, with Notepad.

`credentials` (no file extension):

```ini
[ontodata]
aws_access_key_id = <access key id>
aws_secret_access_key = <secret access key>
```

`config` (no file extension):

```ini
[profile ontodata]
region = us-east-1
```

Don't paste the key anywhere else, and don't commit these files. Terraform reads the `ontodata` profile.

## Create, update and remove

Run these in `deploy/aws/terraform`. Open a new terminal after installing Terraform, so it's on the PATH.

```bash
terraform init
```

```bash
terraform plan
```

`plan` lists every resource it will create, and creates nothing. Then:

```bash
terraform apply
```

It takes about 15–25 minutes, mostly for Redshift and RDS. When it finishes, it prints `app_url`. Open it, enter your LLM key on screen 1, and continue with [Configure and test](deploy-ec2.md#6-configure-and-test). The database, vector store and graph settings are already filled in.

| Task | Command |
|---|---|
| Switch the vector store | `terraform apply -var vector_store=s3vectors` deletes RDS, creates the vector bucket and points the app at it. `-var vector_store=pgvector` switches back. Only one exists at a time. |
| Add Neptune when you reach that test | `terraform apply -var enable_neptune=true` |
| Remove Neptune again, keep the rest | `terraform apply -var enable_neptune=false` |
| Deploy code changes | `terraform apply`. The project zip changes, so the deploy runs again on the same instance. The catalog, ontology and LLM settings are kept; the database, vector store and graph connections are set back to the AWS services. |
| Your IP changed | `terraform apply` updates the port 4000 rule |
| Show endpoints | `terraform output` |
| Show the generated passwords | `terraform output -json passwords` |
| **Remove everything** | `terraform destroy` |

Settings passed with `-var` must be repeated on every `apply`, or the next `apply` changes them back and deletes what they created. To avoid that, put them in `deploy/aws/terraform/terraform.tfvars`, for example `enable_neptune = true` and `vector_store = "s3vectors"`.

## What the deploy does

The SSM association runs on the instance after it starts, and again whenever the project or an endpoint changes. It:

1. Downloads the project zip from the deploy bucket and unpacks it into `/opt/ontodata`.
2. Downloads the JDBC drivers and starts the app and Ontop with `docker-compose.aws.yml`.
3. The first time only: loads [`deploy/aws/redshift-retail.sql`](../deploy/aws/redshift-retail.sql) into Redshift (the same 7 sales tables as the local sample), and creates the read-only `ontodata` user.
4. Saves the Redshift, vector store and Neptune connection settings in the app, for whichever vector store exists.

`terraform apply` waits up to 40 minutes for it to succeed. If it fails, open **Systems Manager → State Manager → ontodata-deploy → Execution history** in the console to see the output. You can also run commands on the instance from **EC2 → ontodata-app → Connect → Session Manager**, for example `docker logs --tail 50 ontodata-app`.

The sample data comes from your local PostgreSQL. To regenerate it, start the local stack and run `node scripts/make-redshift-sample.mjs`.

## Costs

Charges run while resources exist, even when idle. The largest are Neptune, Redshift Serverless (charged only while queries run) and RDS. Run `terraform destroy` when you finish a test session. `apply` recreates everything, and the deploy loads the sample again.
